# Spec map

## Purpose and conventions

`spec-map.md` is the single conformance map for the repository. It ties each of the 24 required tests in Section 22.2 of `draft.md`, and each clause conformance fixtures target, to the fixture ids that exercise them. Every row has a stable, unique `ID`; `fixtures/manifest.json` cites rows through its `spec_map_row` field, so manifest entries and rows cross-reference.

The column set `ID | Check | Draft section | Fixture(s)` is stable. Rows `R01` through `R24` cover the Section 22.2 table in order; ids beginning `CL-` are clause rows, named after the draft section or appendix they test. Fixture ids in the Fixture(s) column have the form of manifest entry ids (`fixtures/README.md`): an evaluation case's id is its case path under `fixtures/`, `outcomes/mapping/` and `outcomes/qualification/` yield three-part ids, an adapter case's id is `adapters/<adapter>/<case>`, the path of its file without `.json`, and a source case's id is `sources/<source>/<case>` in the same way. Rows `COMMON-*`, `IDENT-*`, and `FRESH-*` are the case groups of the common adapter cases in `fixtures/adapters/README.md`; later adapter case groups (`BIND-*`, `TASK-*`, and mechanism cases) are appended the same way, and the columns stay unchanged.

## Refresh procedure

Run this procedure whenever `draft.md` changes.

1. Compute the pin with `python3 scripts/check-spec-map.py --pin`: the sha256 of the draft with the version number of each line that release-please rewrites replaced by `X`, so a release that only bumps the version leaves it unchanged. If the result equals the pinned digest, stop; the map is current.
2. Diff the current draft against the pinned version (recoverable from git history at the commit that recorded the pin); read every changed clause, every change to the Section 22.2 table, and every change to Appendix A.
3. Update the rows. For each changed clause, find the rows that cite it in the Draft section column and update their Check, Draft section, and Fixture(s) cells. A new Section 22.2 test gets a new row with the next `R` number. Ids are never renumbered or reused. A row for a removed test stays, marked retired in the Check column, until no manifest entry cites it. Re-anchor rows whose section numbers moved.
4. Replace the digest in the Draft pin section with the new one and record the commit that carries it.
5. Run `pactfix check manifest` and `pactfix check links`, and fix any dangling id or link before committing.

## Fixture groups

Fixtures live under `fixtures/`. A fixture's group is the first segment of its id. Twelve canonical groups hold evaluation cases: `admission/`, `approval/`, `selection/`, `delegation/`, `outcomes/`, `reputation/`, `learning/`, `privacy/`, `containment/`, `capacity/`, `parse/`, and `transport/`. Each case sits at `fixtures/<group>/<case>/`, or in a single file such as `fixtures/parse/<case>.jws`, with its expected result at `fixtures/expected/<group>/<case>/`. Every later fixture task uses these names. The other groups – `adapters/`, `keys/`, `profiles/`, `schema/`, and `vectors/` – have the layouts that `fixtures/README.md` and the READMEs it names define. Every group that a manifest entry or a row of the conformance map names has a row in the table below.

A fixture id that a row of the conformance map lists is registered when it is the id of a manifest entry. It exists when it is registered, or when its fixture is on disk: `fixtures/<id>` is a file or a directory, or `fixtures/<id>` followed by `.json`, `.yaml`, `.md`, or `.jws` is a file. The Status column records which fixtures of a group are committed, in one of three values:

- `planned`: no fixture of the group is committed. The ids the rows list for the group are reserved, and the manifest has no entry under it; a group with an entry is `partial` or `landed`.
- `partial`: some fixtures of the group are committed, so the manifest has at least one entry under it. A listed id that exists is registered; a listed id that does not exist yet stays reserved. When every listed id of the group exists, the group is marked `landed`.
- `landed`: every id the rows list for the group exists and is registered, and the manifest has at least one entry under the group.

In every status, a listed id whose fixture is on disk is registered. `pactfix check manifest` and `make spec-map` in the source repository report a departure from these rules and a group without a row.
