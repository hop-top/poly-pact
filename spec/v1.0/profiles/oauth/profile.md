# PACT OAuth and OIDC access-token profile

This profile targets spec version 1.0 and wire version 0.1 and is a draft.

## Purpose and status

This is the integration profile ([`TEMPLATE.md`](../TEMPLATE.md)) for a gateway that authenticates agent requests with OAuth 2.0 bearer access tokens and then requires a signed PACT presentation. It supports exactly three token forms:

- **Form I, opaque token with introspection.** An opaque bearer token, validated by RFC 7662 introspection at an endpoint that the gateway's configuration names, with client authentication of the gateway. This is the scenario of [`example_I03.md`](../../examples/example_I03.md).
- **Form E, Microsoft Entra ID v2.0 access token.** A JWT access token issued by the Microsoft identity platform for a registered custom API that requests v2.0 tokens, validated locally against the signing keys of one pinned tenant. This is the inbound token of [`example_I02.md`](../../examples/example_I02.md) and of the operations gateway of [`example_I14.md`](../../examples/example_I14.md).
- **Form G, Google ID token.** An OpenID Connect ID token issued by Google, validated locally as a JWS against the key set of Google's discovery document, for one pinned hosted domain (`hd`) of a Google Workspace or Cloud organization. Google access tokens are opaque and are not a form of this profile (OAUTH-50). The token is the credential of a form G route by a deliberate departure from OAUTH-32. It joins the Google Workspace directory source of [`googledir.md`](../sources/googledir.md) on its `sub`.

It pins issuer, tenant, audience, subject, client, and scope; separates opaque from JWT validation; names the introspection facts that are required; and states how refresh, token storage, native sender proofs, and ID tokens are treated; form G is the one place where an ID token is the credential, and it is still never PACT evidence. The section "Requirement coverage" shows which rule and which case group answers each requirement.

The profile adds no wire field and no protocol requirement. Where it and [`draft.md`](../../draft.md) differ, the draft governs. The uppercase requirement words have the meanings given in draft §3. The rules OAUTH-1 to OAUTH-50 are normative for a claim made under this profile and carry ids so that fixtures and reviews can cite them; they are language-neutral. Every statement about what OAuth, OpenID Connect, Microsoft Entra ID, or Google does cites a primary source listed in the section "Sources", or is an open item in the section "Open items and probes". The conformance cases are listed in section 10 and in the `fixtures` array of [`profile.json`](profile.json); the adapter that implements the rules is separate work, and until it passes those cases this profile cannot support an enforced-support claim (draft §4.4, §22.1).

Shared rules are not repeated here. Identifiers, enrollment, and lifecycle are in [`identity-mapping.md`](../identity-mapping.md) (rules IM-1 to IM-29); the vocabulary of source observation and status time is in [`freshness.md`](../freshness.md); the operation context and the downstream translation are in [`request-binding.md`](../request-binding.md) (rules RB-1 to RB-64). A rule below can be stricter than those documents and none is weaker.

## Rules

### A. Carriage of the access token

**OAUTH-1. Authorization field only.** The access token is taken only from the `Authorization` request header field, with the authentication scheme `Bearer` (RFC 6750 §2.1), matched without regard to case because an authentication scheme is a case-insensitive token (RFC 9110 §11.1). The scheme `DPoP` (RFC 9449 §7.1) is accepted only on an issuer entry whose sender constraint is `dpop` (OAUTH-34). A token in the request body (`access_token`, RFC 6750 §2.2) or in the query (`access_token`, RFC 6750 §2.3) is never read as a credential: resource servers MAY support those methods, and this profile does not. A request whose only token is in the body or the query is a native denial with `NO_CREDENTIAL`. So is a request whose `Authorization` field carries another authentication scheme, such as `Basic`: RFC 6750 §3.1 treats an unsupported authentication method as a request that lacks authentication information, and the challenge carries no error code (OAUTH-4). Such a credential is never read, logged or forwarded.

**OAUTH-2. One credential.** A request with more than one `Authorization` field line, with a credential that does not match the `b64token` syntax of RFC 6750 §2.1, or with a token in the `Authorization` field and also an `access_token` parameter in the query or a form body, is a native denial with `CREDENTIAL_REJECTED`. RFC 6750 §2 forbids a client to use more than one method in a request, and RFC 6750 §3.1 names this case `invalid_request`.

**OAUTH-3. The token is never request data of the operation.** The `Authorization` field is excluded from `OperationContext.headers` (draft §10.2; RB-20), and the `access_token` query parameter, when a request carries one, is refused by OAUTH-2 before binding. The identity is bound through `principal_id` and native authentication (RB-26, RB-27).

**OAUTH-4. Native error responses.** A native denial is answered with the response that RFC 6750 §3 defines: no error code when the request had no credential, `invalid_request` for OAUTH-2, `invalid_token` for every token that failed validation, and `insufficient_scope` for OAUTH-31. The PACT public reason and code are those of section "Results" (OAUTH-40). The response never says which check failed beyond the RFC 6750 error code (draft §13.4).

### B. Issuer entries and form selection

**OAUTH-5. Issuer entries are trusted configuration.** Each issuer entry is installed through the gateway's administrative controls (draft §4.2) and holds: the form (`introspection`, `entra-v2` or `google-id-token`); the issuer identifier; the tenant (OAUTH-37); the accepted audience values; the client allowlist; the required scope of each route it serves (a delegated scope in form E); the sender constraint (`none`, `dpop`, or `mtls`); the token lifetime bound `L`; and, for form I, the introspection endpoint, the client credentials of the gateway, the introspection cache bound `C`, and the resource binding mode (OAUTH-13); for form E, the API's application (client) ID and the key-set bounds of OAUTH-24; for form G, the pinned hosted domain, the OAuth client IDs of the application and the key-set bounds of OAUTH-43 (OAUTH-41). No token, request, discovery document, introspection response, AgentProfile, or signed claim installs or widens an entry (draft §4.2; IM-13).

**OAUTH-6. One entry per route, no fallback.** Each protected route names exactly one issuer entry, and the entry decides the form. The adapter never inspects a token to choose an entry or a form. A token that fails validation under the route's entry is a native denial; it is never tried against another entry, another tenant, another key set, or the other form. A JWT presented on a form I route is sent to introspection like any other token, and its claims are never read locally; any token on a form E or form G route is validated as a JWS and is never introspected, and a form G route never sends a token to any endpoint but the key set of OAUTH-43.

### C. Form I: opaque tokens and introspection

**OAUTH-7. The introspection request.** The adapter sends the token to the entry's introspection endpoint with HTTP `POST` and `application/x-www-form-urlencoded` parameters `token` and `token_type_hint=access_token` (RFC 7662 §2.1). The endpoint URL comes only from the entry; a URL from the token, the request, a discovery response, or an AgentProfile is never contacted (draft Appendix A.2: metadata URLs only within configured trusted origins; draft §8.3: a status reference is not a fetch URL). The connection uses TLS with a server certificate check (RFC 7662 §4).

**OAUTH-8. Client authentication.** The gateway authenticates to the endpoint as an OAuth client with the client authentication method that the authorization server requires and the entry configures (RFC 6749 §2.3). RFC 7662 §2.1 and §4 require the endpoint to demand some form of authorization of the caller, so that it cannot be used to scan for tokens; this profile requires client authentication of the gateway itself and does not use another access token for the call. The gateway's client credentials are never PACT evidence and are never sent anywhere else (draft §4.3, §19).

**OAUTH-9. The response.** A usable response is HTTP 200 with a JSON object (RFC 7662 §2.2), parsed strictly: a duplicate member name, a value of the wrong JSON type, or a body that is not one JSON object makes the response unusable (draft §7.1). An unusable response, an HTTP 401 to the gateway (RFC 7662 §2.3: the gateway's own credentials were rejected), any other error status, a TLS failure, and a timeout are an outage of the source: `DEFERRED` with `DEPENDENCY_UNAVAILABLE` (OAUTH-40), never a denial of the agent.

**OAUTH-10. `active` alone is never enough.** `active` MUST be the JSON value `true`. `active` `false` is a native denial with `CREDENTIAL_REJECTED`; the authorization server returns it for an inactive, unknown, or not-introspectable token and SHOULD NOT say why (RFC 7662 §2.2). With `active` `true`, every fact of OAUTH-11 MUST be present and valid; a response that lacks one is a native denial with `CREDENTIAL_REJECTED`, whatever `active` says (example I03: "`active: true` alone does not authorize the request").

**OAUTH-11. Required facts.** The adapter requires these members of the introspection response (RFC 7662 §2.2 defines each as OPTIONAL; this profile makes them required):

| Member | Requirement |
|---|---|
| `exp` | An integer within 0 to 2^53-1, checked by OAUTH-16 |
| `sub` | A non-empty string, the subject of OAUTH-37 |
| `client_id` | A non-empty string, in the entry's client allowlist, compared exactly (OAUTH-30) |
| `scope` | A string in the syntax of OAUTH-14 |
| `aud`, or the resource binding of OAUTH-13 | Either `aud` names the gateway's resource, or the entry declares that the authorization server binds the token to the gateway's resource |

`iat`, `nbf`, `iss`, `jti`, `token_type`, and `username` are optional. When `iss` is present it MUST equal the entry's issuer identifier exactly. When `nbf` or `iat` is present it is checked by OAUTH-16. When `token_type` is present it MUST be `Bearer`, compared without regard to case because RFC 6749 §5.1 defines the value as case-insensitive, or `DPoP` on an entry whose sender constraint is `dpop` (RFC 9449 §6.2). `username` is a display value and is never used (RFC 7662 §2.2: "human-readable identifier"; IM-5).

**OAUTH-12. Audience.** `aud` is a string or an array of strings (RFC 7662 §2.2, which defines it as in RFC 7519). It satisfies OAUTH-11 when it is, or contains, one of the entry's accepted audience values, compared exactly. A token whose `aud` names no accepted value is refused even when the entry declares a resource binding: RFC 9700 §2.3 obliges every resource server to verify that a token was meant for it and to refuse the request if it was not.

**OAUTH-13. Resource binding without `aud`.** An entry MAY declare the resource binding mode `introspection-scoped`. It is a deployment statement that the authorization server returns `active` `true` to the gateway only for tokens that may be used at the gateway's resource, which RFC 7662 §4 asks of an authorization server for a token that can be used only at certain resource servers. The adapter cannot observe it (deployment requirement DR3, open item OI-4). An entry without that mode requires `aud` (OAUTH-12).

**OAUTH-14. Scope syntax.** `scope` is a space-delimited list of case-sensitive scope tokens (RFC 7662 §2.2, RFC 6749 §3.3: `scope-token = 1*( %x21 / %x23-5B / %x5D-7E )`, order not significant). The adapter splits it at single spaces and returns the tokens as an array in the order received. An empty string, a leading or trailing space, two adjacent spaces, a character outside the scope-token set, and a repeated token are refused (native denial, `CREDENTIAL_REJECTED`), because draft §8.4 compares arrays of unique scalars and the adapter does not repair a value.

**OAUTH-15. Introspection cache.** The entry's cache bound `C` is configurable; `C` = 0 means a new introspection request for every evaluation and is the reference configuration. With `C` greater than 0, a response is reused only while its age, measured from the instant the request that obtained it was sent, is at most `C`, and never at or after the response's `exp` (RFC 7662 §4: a response MUST NOT be cached beyond `exp`). RFC 7662 §4 leaves the cache duration to the designer and warns that a revoked token stays usable while a cached response says it is active; the bound `C` is that window (section 9). The cache is local to the gateway, holds the parsed facts only, and is keyed by a one-way function of the token; it never holds the token text (OAUTH-35). A cached response never stands in for an introspection that fails: once the cached response is outside `C`, an unreachable endpoint is `DEFERRED` (freshness §5).

**OAUTH-16. Time checks.** For form I the adapter applies the time rules of draft §7.5 as `go/core/clock` implements them: `now` < `exp` with no expiry grace, and, when present, `nbf` <= `now` + 5 s and `iat` <= `now` + 5 s. RFC 7662 §4 makes the authorization server responsible for expiry and not-yet-valid checks; the adapter repeats them so that a cached response cannot outlive `exp`.

**OAUTH-17. Lifetime bound in form I.** When both `iat` and `exp` are present, `exp` - `iat` MUST NOT exceed the entry's `L`; a longer lifetime is a native denial with `CREDENTIAL_REJECTED`. The reference configuration for form I is `L` = 3600 s, an illustrative policy choice and not a recommended threshold. Without `iat` the adapter cannot apply the bound, and the observation time of every claim of the token is absent (OAUTH-26, OI-9).

**OAUTH-18. Refresh tokens are not access tokens.** A refresh token is intended for use only with authorization servers and is never sent to resource servers (RFC 6749 §1.5). RFC 7662 §2.1 lets an endpoint introspect refresh tokens too, and its `token_type` member names the access-token type of RFC 6749 §5.1, so the response does not reliably tell the two apart. The adapter sends `token_type_hint=access_token` (OAUTH-7), and the deployment states that its authorization server answers `active` `true` to the gateway only for access tokens (deployment requirement DR3; open item OI-5).

### D. Form E: Microsoft Entra ID v2.0 access tokens

**OAUTH-19. v2.0 tokens for the custom API.** The API's application registration sets `requestedAccessTokenVersion` to 2, which produces v2.0 access tokens independently of the endpoint the client uses (Microsoft: app manifest reference; access tokens, "Token ownership"). The token's `ver` claim MUST be the string `2.0` (Microsoft: access token claims reference). A v1.0 token, whose metadata lives at the v1.0 endpoint (Microsoft: access tokens, "v1.0 and v2.0 tokens"), is refused. The validation rules of this section apply only to tokens issued for registered APIs; Microsoft states that its documentation of access tokens does not apply to tokens for Microsoft-owned APIs (Microsoft: access tokens), and this profile never validates a token issued for Microsoft Graph or another Microsoft API (section 6).

**OAUTH-20. JWS only.** The token is a JWS in compact serialization: three base64url segments separated by `.`. A token with five segments (a JWE) or any other shape is a native denial with `CREDENTIAL_REJECTED`. The header MUST carry `typ` `JWT`, which Microsoft documents as the constant value for its access tokens (Microsoft: access token claims reference, header claims). Because the token is not explicitly typed as an access token in the sense of RFC 9068 §2.1 (`at+jwt`), RFC 8725 §3.11 typing gives no protection against an ID token here; OAUTH-32 does.

**OAUTH-21. Algorithm.** The header `alg` MUST be in the entry's algorithm allowlist, and the reference allowlist is `RS256`. Microsoft states that Entra ID signs tokens with industry-standard asymmetric algorithms, "such as RS256" (Microsoft: access tokens, "Validate the signature"), and the discovery document of the tenant lists only `RS256` for ID token signing (probe E1); the algorithm of access tokens is not separately published (open item P5). `none` and every symmetric algorithm are refused (RFC 8725 §3.1: the caller specifies the supported algorithms and no other is used; each key is used with exactly one algorithm).

**OAUTH-22. Key selection.** The header MUST carry `kid`; v2.0 tokens carry only `kid` and not `x5t` (Microsoft: access tokens, "Validate the signature"). The key is the member of the key set (OAUTH-23) whose `kid` equals the header's `kid`, compared as case-sensitive strings (RFC 7515 §4.1.4, RFC 7517 §4.5). The member MUST have `kty` `RSA` and, when `use` is present, `use` `sig`. When the member carries an `issuer` property, it MUST equal the entry's issuer identifier exactly (Microsoft: access tokens, "Validation of the signing key issuer"; probe E2 shows each key of a tenant key set carrying the tenant issuer). Two members with the same `kid` are refused: RFC 7517 §4.5 asks for distinct values and does not require them. The header members `jku`, `x5u`, `jwk`, and `x5c` are ignored and never fetched or used (RFC 8725 §3.10). A header with `crit` naming any parameter is refused, because this profile understands no JWS extension (RFC 7515 §4.1.11). No key from any other source is used.

**OAUTH-23. Discovery of the configured issuer only.** The key set is reached from the OpenID Connect discovery document of the entry's issuer identifier, fetched with HTTP `GET` from the issuer identifier followed by `/.well-known/openid-configuration` (OpenID Connect Discovery 1.0 §4, §4.1; Microsoft: access tokens, "v1.0 and v2.0 tokens", for the v2.0 path). The document is used only if its `issuer` member is identical to the issuer identifier (Discovery §4.3); otherwise it is discarded and nothing in it is used. Its `jwks_uri` MUST use `https` (Discovery §3) and MUST be within the configured trusted origins (draft Appendix A.2); the reference is the origin `https://login.microsoftonline.com`. The tenant-independent documents of `common`, `organizations`, and `consumers`, whose `issuer` is a template with `{tenantid}` (Microsoft: access tokens, "Multitenant applications"; probe E1), are never used. Microsoft recommends discovering and caching keys per tenant with the tenant-specific endpoint (Microsoft: signing key rollover, "Best practices"). The `appid` query parameter for custom signing keys (Microsoft: access tokens, "Validate the signature") is not supported (section 6).

**OAUTH-24. Key-set refresh and outage.** Keys roll over periodically and, in an emergency, at once, with no guaranteed interval (Microsoft: signing key rollover). The adapter refreshes the key set every `K` seconds, accepts a cached key for at most `T` seconds after the successful fetch that produced it, and, when a token names a `kid` that is not in the held set, fetches the set again at most once every 300 s, as Microsoft's key refresh procedure describes (Microsoft: signing key rollover, "Keys metadata caching algorithm"). The reference configuration follows that page: `K` = 3600 s and `T` = 86400 s; probe E2 observed `Cache-Control: max-age=86400` on the key set. These are illustrative policy choices. A `kid` still unknown after a successful fetch is a native denial with `CREDENTIAL_REJECTED`. When no key set younger than `T` is held and a fetch fails, or when a refresh for an unknown `kid` fails, the result is `DEFERRED` with `DEPENDENCY_UNAVAILABLE`. A held key set never outlives `T` because the source is down (freshness §5).

**OAUTH-25. Signature.** The signature is verified with the selected key and the allowlisted algorithm before any claim is read (Microsoft: access tokens, "validate the signature of the token and the issuer against the values in the OpenID discovery document"). A token that fails is a native denial with `CREDENTIAL_REJECTED`.

**OAUTH-26. Issuer and tenant.** `iss` MUST equal the entry's issuer identifier exactly, which for a single-tenant API is the whole issuer check (Microsoft: access tokens, "Single tenant applications"; OpenID Connect Core §2 makes `iss` a case-sensitive URL). `tid` MUST be present and MUST equal the entry's tenant octet for octet; the entry's tenant is a GUID in lower case with hyphens, as the tenant discovery document spells it (probe E1). The adapter also checks that the path of `iss` is `/{tid}/v2.0` for that `tid`, as Microsoft asks of an application that uses `tid` as a trust boundary (Microsoft: access tokens, "Validate the issuer"). Claims are interpreted within the tenant: the same `sub` under two tenants names two users (Microsoft: access tokens, note on tenant-independent metadata).

**OAUTH-27. Audience.** `aud` MUST equal one of the entry's accepted audience values exactly. For v2.0 tokens Microsoft documents `aud` as always the client ID of the API, a GUID (Microsoft: access token claims reference; claims validation, "Validate the audience"), so the reference configuration accepts the API's application (client) ID. A deployment MAY also accept the API's Application ID URI, which Microsoft's access token page names as an accepted audience of web APIs in general (Microsoft: access tokens, "Validate tokens"); whether a v2.0 token ever carries it is open item P3. A token for another resource, Microsoft Graph included, is refused: accepting a token meant for another resource is the confused deputy problem (Microsoft: access tokens, "Validate tokens").

**OAUTH-28. Time checks.** `exp`, `nbf`, and `iat` MUST be present, and the adapter applies `go/core/clock` `CheckWindow` to them with the baseline skew of 5 s: `nbf` <= `now` + 5 s, `iat` <= `now` + 5 s, and `now` < `exp`, with no grace after `exp` (draft §7.5). This is stricter than the leeway that RFC 7519 §4.1.4 and §4.1.5 and RFC 9068 §4 allow.

**OAUTH-29. Lifetime bound in form E.** `exp` - `iat` MUST NOT exceed the entry's `L`. Microsoft assigns a default lifetime of 60 to 90 minutes, configurable from 10 minutes to one day, and long-lived tokens of up to 28 hours when client and resource support continuous access evaluation (Microsoft: access tokens, "Token lifetime"; configurable token lifetimes). The reference configuration is `L` = 5400 s, the upper end of the default range, an illustrative policy choice. A deployment that raises `L` raises the achievable `max_age` of section 8 and the revocation window of section 9 with it.

**OAUTH-30. Client.** In form E the client is `azp`, the application ID of the client using the token, present only in v2.0 tokens (Microsoft: access token claims reference). In form I it is `client_id` (RFC 7662 §2.2). The value MUST be in the entry's client allowlist, compared exactly. `appid`, a v1.0 claim, is never read. An allowlisted client that is a public client (`azpacr` `0`, Microsoft: access token claims reference) has no client authentication behind its identifier; a deployment MAY require `azpacr` `1` or `2` in the entry, and the limit is disclosed in section 9.

**OAUTH-31. Delegated scope.** In form E the token MUST carry `scp`, a space-separated list of scopes that is "only included for user tokens" (Microsoft: access token claims reference), parsed by the syntax of OAUTH-14; an absent or empty `scp` is a native denial with `CREDENTIAL_REJECTED` (Microsoft: claims validation, "Validate the actor": `scp` is absent in app-only tokens and ID tokens). A token that carries `roles` and no `scp` is an app-only token and is refused (section 6). The required delegated scope of the route (OAUTH-5) MUST be a member of the token's scope list, in both forms; this check is part of `authorize_native`, because a token that is valid but lacks the scope is an authorization failure, `insufficient_scope` with HTTP 403 (RFC 6750 §3.1), and not a failed authentication. `scp` lists the scopes "for which the client application has requested (and received) consent" and can include preauthorized scopes (Microsoft: access token claims reference). The resource server sees consent only through `scp`, so missing consent shows as a missing scope and ends here as a native denial. PACT never adds a scope (example I03).

**OAUTH-32. ID tokens are never access tokens.** An ID token is evidence of an authentication event for a client: its `aud` MUST contain the client's own `client_id` (OpenID Connect Core §2), and Microsoft states that an ID token is not to be used to call an API (Microsoft: ID tokens). In form E an ID token fails OAUTH-27 when its audience is the client and OAUTH-31 when the client is the API itself, because an ID token carries no `scp` (Microsoft: claims validation). In form I the authorization server decides what it introspects, and this profile accepts only what OAUTH-10 and OAUTH-11 accept. Form G is the one exception: the credential of a form G route is an ID token, by the decision recorded in OAUTH-41, and it is never accepted on a route of form I or form E. Section F covers ID tokens offered as evidence.

**OAUTH-33. Claims never used.** `sub` in form E is a pairwise identifier per application (Microsoft: access token claims reference) and is not part of the identity (OAUTH-37). `email`, `preferred_username`, `upn`, `unique_name`, and `name` are display values and are never used for identity or authorization (Microsoft: claims validation, "Validate the subject"; IM-5). `groups`, `roles`, and `wids` are not read; a groups overage replaces the list by a reference to Microsoft Graph (Microsoft: access token claims reference, "Groups overage claim"), and this profile claims no membership fact from a token (section 8.1). A deployment that needs a membership or account-state fact uses a directory source with its own source document, embedded as a row of section 8.1: the SCIM provisioning endpoint of [`scim.md`](../sources/scim.md), joined on the `oid` of form E (SC-10); for form G, the Google Workspace directory source of [`googledir.md`](../sources/googledir.md), joined on `sub` (GD-7); or, for account state that an identity provider transmits, the Shared Signals receiver of [`ssf.md`](../sources/ssf.md). `aio`, `rh`, and other claims marked opaque are not read (Microsoft: access token claims reference).

### E. Sender constraints, refresh, and storage

**OAUTH-34. Sender constraints are native.** PACT does not implement DPoP (RFC 9449) or mutual-TLS certificate-bound tokens (RFC 8705), and the adapter verifies neither a DPoP proof nor a certificate binding. An entry declares its sender constraint:

- `none`: a token that carries `cnf`, as a JWT claim (RFC 7800 §3.1) or as an introspection member (RFC 9449 §6.2, RFC 8705 §3.2), is refused. A resource server that supports DPoP and Bearer MUST reject a DPoP-bound token received as a bearer token (RFC 9449 §7.2), and a certificate-bound token is rejected when its certificate does not match (RFC 8705 §3.2); with no verifier in the path neither can be checked, so the token is not accepted as a bearer token.
- `dpop` or `mtls`: the deployment's native sender-constraint verifier runs in the request path before `authenticate_native` and verifies the proof as RFC 9449 §7.1 or RFC 8705 §3 requires (deployment requirement DR4). The adapter checks only that `cnf` is present with `jkt` (for `dpop`) or `x5t#S256` (for `mtls`), and that the native verifier reports success for this request through the gateway's authenticated context, never through a request header. A token without that `cnf` member, and a request without a reported success, is a native denial with `CREDENTIAL_REJECTED`.

A key named by `cnf` is never the holder key: the enrolled `holder_jkt` MUST differ from `cnf.jkt`, and a key that a token is bound to never enrolls or binds the holder key (IM-21; draft §6.2). `authenticate_native` reports the token's `cnf` as the attribute `cnf` of the principal, `{"jkt": <thumbprint>}` or `{"x5t#S256": <thumbprint>}`, and compares nothing; `resolve_agent_binding` is not given the token. The validator compares `cnf.jkt` with the `holder_jkt` of the binding that `resolve_agent_binding` selected and refuses equality with `INVALID_PROOF`. This mirrors MTLS-9 of the [mTLS profile](../mtls/profile.md).

**OAUTH-35. No token storage.** The gateway is not a token store. An access token, an introspection request or response body, a refresh token, an ID token, and the gateway's client credentials never appear in an AgentProfile, a receipt, an `OutcomeReport`, a `CheckResult`, an error, or a log (draft §19; example I02, "Token and credential boundaries"). The only retained data are the parsed facts of a cached introspection response under OAUTH-15 and the key set under OAUTH-24. The `SourceRef` of a claim is the token's `jti` (form I) or `uti` (form E, the token identifier that Microsoft documents as equivalent to `jti`), or empty when the token carries none, as every form G token does; it is never a digest of the token.

**OAUTH-36. Refresh is native.** PACT does not obtain, refresh, or exchange tokens. A refreshed access token is a new credential with its own issue time and identifier: every request is authenticated with the token it carries, and nothing about identity is carried over from an earlier token or request. A refresh can return a token with narrower scope (RFC 6749 §1.5, §6), and a token issued for a contract request may be replaced before the protected request. Authority changes on refresh are caught as follows: a different principal is `CONTEXT_MISMATCH` (OAUTH-39); a different client is a different workload, on which `resolve_agent_binding` answers `UNKNOWN` for the presented agent and reports it enrolled for another workload, `CONTEXT_MISMATCH` (OAUTH-38, OAUTH-40; identity-mapping IM-11, §8); a different tenant fails OAUTH-26 or yields another principal; a scope list without the route's scope fails OAUTH-31; and a field rule over the scope list compares the values of the new token (section F). The gateway never forwards the inbound token downstream (RB-51) and never uses it to obtain another token; an on-behalf-of exchange belongs to form D of the [Graph profile](../graph/profile.md) and is outside this profile.

### F. Identity, binding, and claims

**OAUTH-37. Principal.** The principal is `oauth:{issuer-id}:{tenant}:{subject}` (identity-mapping §3.3), written under IM-2:

- Form E: `issuer-id` is the issuer identifier `https://login.microsoftonline.com/{tid}/v2.0`; `tenant` is `tid`; `subject` is `oid`. `oid` is the immutable identifier of the user or service principal, the same across applications in one tenant (Microsoft: access token claims reference), which is the case identity-mapping §3.3 names for `oid`. A token without `oid` is a native denial with `CREDENTIAL_REJECTED`; whether `oid` and `tid` are present without the `profile` scope is open item P1. Microsoft recommends `tid` and `oid` together as the key of a user's data (Microsoft: claims validation, "Validate the subject").
- Form I: `issuer-id` is the entry's issuer identifier; `tenant` is the entry's configured tenant, or the constant `none` for an authorization server with no tenant concept, which this profile declares as identity-mapping §3.3 asks; `subject` is `sub`. RFC 7662 §5 allows an authorization server to return different identifiers to different protected resources; the identifier is stable for this gateway, which is all IM-5 needs.

- Form G: `issuer-id` is the issuer identifier `https://accounts.google.com`; `tenant` is the pinned `hd`; `subject` is `sub` (OAUTH-48). Identity-mapping §3.3 names `sub` for an issuer with no per-tenant object identifier, and Google documents `sub` as never reused and never changed. A token without `sub`, or with an `hd` other than the entry's, is a native denial.

Informative example (form E, fictional tenant and object IDs): `oauth:https%3A%2F%2Flogin.microsoftonline.com%2F7c1d0b3a-5e7f-4a53-9a43-2f7d1f0e9b11%2Fv2.0:7c1d0b3a-5e7f-4a53-9a43-2f7d1f0e9b11:3f2a9d54-0c1e-4d7e-8f1a-5b6c7d8e9f01`.

**OAUTH-38. Workload and binding.** The workload is the client: `oauth:{issuer-id}:{tenant}:{client}`, where `client` is `azp` (form E), `client_id` (form I), or `azp` else `aud` (form G, OAUTH-48), written under IM-2. Identity-mapping §3.4 asks the profile to state this form; it has the shape of the client workloads of the common identity fixture `IDENT-03`. The enrollment record names this workload in the gateway's realm. `resolve_agent_binding` is given the realm, the workload, and the agent ID the presentation names, and returns that agent's enrollment on the workload, or `UNKNOWN` when there is none, together with whether the agent is enrolled for another workload of the realm (draft §17.1; IM-11); the workload alone never names an agent (IM-16, IM-18). One client serves one agent: a client workload with more than one enrollment in force is a configuration error, with the consequence that identity-mapping §5 states, and shared clients are unsupported (IM-19; section 6). Which users an agent may act for is native delegation (`/attributes/delegation/authority_ref`, check `native-delegation-v1`, draft §17.5), not enrollment: an agent is never bound to a user alone (identity-mapping §3.4).

**OAUTH-39. Principal binding.** The principal at contract issuance is bound by the contract's `operation_digest` and compared by the validator with the principal authenticated for the actual request (draft §9.1, §11.3 step 5). The baseline check `native-principal-binding-v1`, which the validator evaluates (draft §17.5), compares the presented `/attributes/environment/principal_id` with the principal of OAUTH-37 and returns `FAIL` with `CONTEXT_MISMATCH` when they differ (example I03, "A token subject or client other than the enrolled one presented"). It compares identifiers and not tokens: a token refreshed between issuance and evaluation for the same principal passes. A different client is a different workload, handled by OAUTH-36, OAUTH-38, and OAUTH-40. The adapter implements neither comparison.

**Native claims.** The approved native paths of `read_native_claim` at mapping revision `pact-oauth-1` are:

| Native path | Value | Comparison (draft §8.4) | Informative profile path |
|---|---|---|---|
| `/oauth/principal_id` | The principal of OAUTH-37 | `equal` | `/attributes/environment/principal_id` |
| `/oauth/tenant_id` | The `tenant` component of OAUTH-37 | `equal` | `/attributes/environment/tenant_id` |
| `/oauth/client_id` | The workload of OAUTH-38, the namespaced client | `equal` | `/attributes/environment/client_app_id` (example I02), `/attributes/environment/oauth_client_id` (example I03) |
| `/oauth/scopes` | The scope list of OAUTH-14 or OAUTH-31, as an array of unique strings | `subset` | `/attributes/environment/oauth_scopes` |

Any other path returns `UNSUPPORTED_REQUIREMENT`, and so does `/oauth/scopes` of a form G principal (OAUTH-49). The client is returned in its namespaced form, so that a same-spelled client of another issuer or tenant never matches (draft §8.5, §17.2); the examples show the bare client ID and are informative. Scope strings are returned as issued, because OAUTH-6 ties every route to one entry and so to one issuer. For `subset`, every scope the profile presents MUST occur in the token's scope list (draft §8.4). A presented array that is empty or does not contain the scope the requirement needs satisfies `subset` and is still insufficient, so the field rule's schema requires it, for example with `minItems` 1 and `contains` with a `const` of the scope (draft Appendix A.1 lists both keywords), as example I03 asks ("a matching empty or irrelevant scope array is insufficient").

The times of a claim follow freshness §4.1, token row. `ObservedAt` is the token's `iat`, or empty when form I returns none. In form I, `StatusCheckedAt` is the instant the introspection request that produced the facts was sent, which is not later than the authorization server's check. In forms E and G, `StatusCheckedAt` is empty: a JWT access token of this profile, and a Google ID token, has no status mechanism, because no revocation or status list is supported in wire version 0.1. Freshness §4.1 states the consequence: "A token with no status mechanism cannot meet any status limit". A field rule over a form E or form G path therefore never passes. When the value is demonstrably different from the presented one, the rule fails (`INADMISSIBLE`, draft §11.4); otherwise it is `UNKNOWN` with `UNSUPPORTED_REQUIREMENT` and the decision is `DEFERRED` (freshness §3.1, rule 6, and §4.2, convention 2). In forms E and G the principal and the client are still enforced, by `authenticate_native`, OAUTH-38, and OAUTH-39; the scope of form E is enforced by `authorize_native`, and a form G route has none (OAUTH-49). Whether the freshness profile should define a status bound for snapshot sources with no status mechanism is open item OI-1.

**ID tokens as evidence.** An ID token is not a PACT `Evidence` artifact and never satisfies an `evidence` rule: an evidence artifact is a signed PACT artifact of its own `typ` (draft §7.3), checked under its issuer's configured claim-path authority (draft §8.3), and a validator enforces artifact types first (draft §11.3, step 1). An ID token placed in a presentation's evidence array is therefore not accepted, and no adapter of this profile converts one into evidence (example I02).

### H. Form G: Google ID tokens

**OAUTH-41. Form G entry and credential.** A form G entry has the form `google-id-token`; the issuer identifier `https://accounts.google.com`, which is the `issuer` of Google's discovery document and the only issuer this form accepts; the tenant, the pinned hosted domain (OAUTH-46); the accepted audience values, which are the OAuth 2.0 client IDs of the deployment's application (Google: OpenID Connect, ID token claims: `aud` "must be one of the OAuth 2.0 client IDs of your application"); the client allowlist (OAUTH-48); the lifetime bound `L`; the algorithm allowlist; the key-set bounds `K` and `T`; the trusted origins of the key set; and the sender constraint `none`. The credential is the ID token in the `Authorization` field, carried as OAUTH-1 and OAUTH-2 say. This is the owner's decision for this form and a departure from OAUTH-32, which keeps ID tokens out of forms I and E: a Google access token is opaque, and the page that documents Google's `tokeninfo` endpoint says that it "is useful for debugging but for production purposes, retrieve Google's public keys from the keys endpoint and perform the validation locally" and that "Requests to the debugging endpoint may be throttled or otherwise subject to intermittent errors" (Google: OpenID Connect, "Validating an ID token"; [`googledir.md`](../sources/googledir.md), section 10). A form G entry never reads a token as anything but an ID token (OAUTH-50).

**OAUTH-42. JWS, algorithm, header, key.** The token is a JWS in compact serialization of three segments, checked before any request is made; a token of another shape, a JWE and an opaque Google access token included, is a native denial with `CREDENTIAL_REJECTED`. The header `alg` MUST be in the entry's allowlist, and the reference allowlist is `RS256`: the discovery document lists `id_token_signing_alg_values_supported` `["RS256"]`, in the sample of Google's page and in probe G1, and every member of the key set carries `alg` `RS256` (probe G2); the prose of the page names no algorithm. `none`, every symmetric algorithm and every other algorithm are refused (RFC 8725 §3.1). The header MUST carry `kid`, matched as OAUTH-22 matches it. The key is a member of the key set of OAUTH-43 with `kty` `RSA`, `use` `sig` when it has `use`, `alg` `RS256` when it has `alg` (RFC 7517 §4.4: the algorithm intended for use with the key; RFC 8725 §3.1: each key is used with exactly one algorithm), an `issuer` property equal to the entry's issuer identifier when it has one, and a modulus of at least 2048 bits (RFC 7518 §3.3); two members with one `kid` are refused. The header members `jku`, `x5u`, `jwk` and `x5c` are ignored and never fetched or used, and a header with `crit` is refused, as in OAUTH-22. A header `typ` that is present MUST be `JWT`; no page read states the `typ` of a Google ID token, so an absent `typ` is accepted and the question is probe P9. A `typ` of `at+jwt` marks an RFC 9068 access token (RFC 9068 §2.1) and is refused (RFC 8725 §3.11). The signature is verified before any claim is read (OAUTH-25).

**OAUTH-43. Discovery, key set, and its cache.** The key set is reached from the discovery document at the issuer identifier followed by `/.well-known/openid-configuration`, which is the URI that Google asks an application to hard-code. The document is used only if its `issuer` is identical to the entry's issuer identifier (Discovery §4.3), and its `jwks_uri` MUST use `https` and be within the entry's trusted origins; the reference origin is `https://www.googleapis.com`, the origin of the `jwks_uri` in probe G1. Google says that its keys change infrequently and "you can cache them using the cache directives of the HTTP response", and that for the discovery document "Standard HTTP caching headers are used and should be respected" (Google: OpenID Connect). The adapter therefore keeps a key set only as long as the response that carried it says, by RFC 9111:

- A response with `no-store` or `no-cache` is not reused: the set serves the validation that fetched it and no other (RFC 9111 §5.2.2.4, §5.2.2.5).
- Otherwise the freshness lifetime is the `max-age` directive (§5.2.2.1), or, with none, `Expires` minus `Date`, or minus the time of receipt when there is no `Date` (§5.3, §4.2.1). `s-maxage` is for shared caches and is not read. Freshness information that is invalid or given twice, such as a `max-age` that is not a non-negative integer, two `max-age` directives, an `Expires` that is not a date or is `0`, is stale information (§4.2.1, §5.3).
- A response with no freshness information is fresh for `K` (heuristic freshness, §4.2.2). A lifetime is never longer than `T`.
- The `Age` of the response is subtracted (§4.2.3, §5.1); an `Age` that is not a non-negative integer is ignored. A key set is fresh while its lifetime exceeds its age, so a key set whose age equals its lifetime is stale (§4.2).
- A key set that is not fresh is fetched again before any use. When that fetch fails the result is `DEFERRED` with `DEPENDENCY_UNAVAILABLE`: a stale key set is never used, because a cache MUST NOT generate a stale response unless it is permitted to (RFC 9111 §4.2.4), this profile gives no such permission, and Google's response for the key set carries `must-revalidate` (probe G2; RFC 9111 §5.2.2.2).
- A fresh key set that lacks the `kid` is fetched again at most once every 300 s, as in OAUTH-24; a `kid` still unknown after a successful fetch is a native denial. The 300 s is a policy choice, and the page gives no figure.
- The discovery document is fetched again at each fetch of the key set and is never held, so its cache headers are respected by never reusing it.

`K` and `T` are as for form E, `K` = 3600 s and `T` = 86400 s in the reference configuration, illustrative policy choices; probe G2 observed `Cache-Control: public, max-age=20123, must-revalidate, no-transform`.

**OAUTH-44. Issuer.** `iss` MUST be `https://accounts.google.com` or `accounts.google.com`, compared exactly (Google: OpenID Connect, validation step 2 and the claim table: "Always `https://accounts.google.com` or `accounts.google.com` for Google ID tokens"). Any other value is refused, the form with a trailing slash that the RISC page uses ([`googledir.md`](../sources/googledir.md), section 9) included. The `issuer-id` of the principal is the entry's issuer identifier, `https://accounts.google.com`, whichever of the two spellings the token carries, so that one identity has one identifier (IM-2; identity-mapping §3.3).

**OAUTH-45. Audience.** `aud` MUST be a string equal to one of the entry's accepted audience values (Google: "Verify that the value of the `aud` claim in the ID token is equal to your app's client ID"). An array is refused, because Google's page gives `aud` as one client ID, and a token for another application's client is refused: accepting it is the confused deputy problem (OAUTH-27).

**OAUTH-46. Hosted domain.** `hd` MUST be present and MUST equal the entry's tenant octet for octet. Google states that `hd` is "The domain associated with the Google Workspace or Cloud organization of the user. Provided only if the user belongs to a Google Cloud organization. You must check this claim when restricting access to a resource to only members of certain domains. The absence of this claim indicates that the account does not belong to a Google hosted domain." The `hd` parameter of the authentication request is a UI optimization: "Don't rely on this UI optimization to control who can access your app, as client-side requests can be modified. Be sure to validate that the returned ID token has an `hd` claim value that matches what you expect" (Google: OpenID Connect, authentication URI parameters). A token with no `hd`, an empty or non-string `hd`, another domain, a subdomain, or another spelling of the domain is a native denial. The domain of `email` never stands for `hd`: "You also can't rely on the domain of the `email` claim to identify users of Google Workspace or Cloud organizations; use the `hd` claim instead". The tenant is configuration; the claim confirms it.

**OAUTH-47. Times.** `exp` and `iat` MUST be present integers (Google: both "always"). `nbf` is not in Google's claim list: when it is present it is checked, and when it is absent it is taken as `iat`. The adapter applies `go/core/clock` `CheckWindow` with the baseline skew of 5 s: `nbf` <= `now` + 5 s, `iat` <= `now` + 5 s, and `now` < `exp`, with no grace after `exp` (Google: `exp` is the "Expiration time on or after which the ID token must not be accepted"; draft §7.5). `exp` MUST be later than `iat`, and `exp` - `iat` MUST NOT exceed the entry's `L`. The reference configuration is `L` = 3900 s, the lifetime of the example ID token on Google's page (`iat` 1353601026, `exp` 1353604926), an illustrative policy choice: no page states the lifetime of the tokens Google issues (probe P10).

**OAUTH-48. Subject, principal and workload.** The principal is `oauth:{issuer-id}:{tenant}:{subject}` (OAUTH-37) with `issuer-id` the issuer identifier `https://accounts.google.com`, `tenant` the pinned `hd`, and `subject` the `sub` claim, which Google describes as "unique among all Google Accounts and never reused" and "never changed", and tells applications to use "as the unique-identifier key for the user", at most 255 case-sensitive ASCII characters. The adapter requires 1 to 255 visible ASCII characters and refuses anything else. `sub` is the only identity claim: `email` "may not be unique to this account and could change over time", and Google says "Don't use the `email` field as a unique identifier for a user. Always use the `sub` field". A token without `sub` is a native denial whatever else it carries. `email`, `email_verified`, `name`, `given_name`, `family_name`, `picture` and `locale` are display values and are never used (IM-5). The workload is `oauth:{issuer-id}:{tenant}:{client}` (OAUTH-38) where `client` is `azp` when the token has it and `aud` otherwise; Google defines `azp` as "The client_id of the authorized presenter", "only needed when the party requesting the ID token is not the same as the audience of the ID token". The client MUST be in the entry's client allowlist, compared exactly. `azp` and not `aud` names the workload when the token has both: `aud` names the party the token is for, which "must be one of the OAuth 2.0 client IDs of your application" (Google: OpenID Connect), and for an ID token of a service account its value "can be freely chosen by the token requester", while `azp` is "The service account that requested the token" (Google Cloud: token types). Without `azp`, the party that requested the token is its audience, because `azp` is the claim that names a requesting party other than the audience; `aud` then names that client. The workload is the client the token was issued to, not the party that sends it: no page read says that the two are the same, so a token forwarded by another party is attributed to the client it was issued to, and the holder-key proof, not the client, distinguishes the agent (draft §6.2; section 9). The `sub` is the local part on which the Google Workspace directory source joins ([`googledir.md`](../sources/googledir.md), GD-7 and GD-9).

**OAUTH-49. No scope, no status.** An ID token carries no scope, so OAUTH-31 does not apply to form G: a route of a form G entry requires no scope (an adapter configuration that names one is refused), and `/oauth/scopes` of a form G principal is `UNSUPPORTED_REQUIREMENT`. `/oauth/principal_id`, `/oauth/tenant_id` (the pinned `hd`) and `/oauth/client_id` are read as in section F, with `ObservedAt` the `iat`, no `StatusCheckedAt` (an ID token has no status mechanism in wire version 0.1, as a form E token has none), and no `SourceRef`, because Google documents no `jti`. A field rule over a form G path therefore never passes, as for form E (open item OI-1). A token that carries `cnf` is refused, because a form G entry's sender constraint is `none` (OAUTH-34).

**OAUTH-50. Not evidence; no access-token form.** A Google ID token is the credential of its route and is never a PACT `Evidence` artifact (section F, "ID tokens as evidence"). Google access tokens are not a form of this profile: the adapter never calls `tokeninfo` or any other Google endpoint with a token, and a token on a form G route that is not a three-segment JWS is a native denial before any request. The access-token form is deferred (open item OI-10).

## 1. Claim scope

It declares the `full` conformance profile and the `https` transport profile, both at version 0.1, and uses [`request-binding.md`](../request-binding.md) at version 0.1 with the stricter path grammar of section 2.

## 2. Protected routes and actions

Two reference routes are claimed, one for each of forms I and E. Form G has no reference route and no row of the mapping table at `pact-oauth-1`: a deployment that serves a route under a form G entry lists it in its own profile and installs its own mapping revision, and the route requires no scope (OAUTH-49). The route patterns follow examples I03 and I02; a deployment that claims other routes lists them in its own profile. The PACT endpoints of draft §13.2 that require native authentication are covered in section 5 (B5).

| ID | Route pattern | Method | Action | Resource mapping |
|---|---|---|---|---|
| R1 | `/customers/{customer_id}` | `GET` | `crm.customer.read` | `crm-customer:{customer_id}`, from the path parameter as bound. Served under issuer entry E1 (form I). The customer permission of the principal is native authorization (`authorize_native`) |
| R2 | `/mail/messages` | `GET` | `mail.message.list` | `mailbox:{principal_id}`, from the authenticated principal (RB-40). Served under issuer entry E2 (form E) |

The mapping table at revision `pact-oauth-1`, in the form of RB §5.1:

| Row | Method | Path pattern | Path parameters and grammar | Query parameters read | Body | Action | Resources |
|---|---|---|---|---|---|---|---|
| R1 | `GET` | `/customers/{customer_id}` | `customer_id`: 1 to 64 of `A`-`Z`, `a`-`z`, `0`-`9`, `-` | none | none | `crm.customer.read` | `crm-customer:{customer_id}` |
| R2 | `GET` | `/mail/messages` | none | none | none | `mail.message.list` | `mailbox:{principal_id}` |

- The binding follows draft §10.2 and RB-1 to RB-30. Both routes are stricter than RB-8: a path with a `.` or `..` segment is refused with `INVALID_MESSAGE`. The `customer_id` grammar admits no `.`, so it has one spelling (RB-34).
- A query on R1 or R2 is covered by `target_uri`, is not read for the action or resources, and is never forwarded downstream (RB-36, RB-50). A query parameter named `access_token` is refused by OAUTH-2.
- Headers (RB-18): the allowlist is `accept` and `prefer`, so a change to either is a context mismatch. `content-type` is covered whenever a body is present, and both rows refuse a body (RB-37). For `if-match`, `if-none-match`, and `idempotency-key`, deployment requirement DR5 records that the read on each route gives them no action-changing meaning. The `Authorization`, `DPoP`, and `PACT-Presentation` fields are never covered (RB-20, RB-21).
- R1 is executed by the CRM API's own read, inside the resource server whose filter chain is the gateway; no downstream HTTP request carries the token (OAUTH-36), and DR1 closes every other way to the read.
- R2 is executed by a Microsoft Graph call under a separate delegated token that the gateway obtains on the user's behalf (example I02, steps 6 and 7). The translation row of R2, its executor, and its fixed downstream query belong to the [Graph profile](../graph/profile.md): R2 is the inbound side of its row GD1 (form D), whose mapping row is stricter than R2 and is the one used on a deployment that claims both (that profile, section 1). This profile claims the inbound authentication and binding of R2 only; R2 supports an enforced claim end to end only together with that profile (open item OI-7, closed).
- Example I14 uses an inbound token of form E for its operations gateway. Its activation check and its downstream Azure call are not routes of this profile (section 6).

### 8.1 Membership and status sources

F1, F2 and F6 supply the identity of the authenticated principal, and F1 also its token status, so they are listed again here. F1 is a live query of the authorization server with no change feed. F2 and F6 are tokens the client presents, with no live check. The enrollment registry and the hold store supply binding and hold status, not membership, role, or account-state facts, so they are not listed. No token supplies a group or role fact, and the `account_state` of F1 is the token's status (below): this profile claims no membership fact from a token (OAUTH-33). ## 9. Residual limits

| Limit | What remains true | Bound or disclosure |
|---|---|---|
| Post-read | Data already returned to the agent is not recalled by a later revocation; an executed operation is not undone by revoking its receipt (draft §18); no egress or data-use control is claimed (draft §17.4) | Disclosed here; no bound |
| Revocation propagation: form I token (F1) | A revocation at the authorization server reaches the gateway at the next introspection after it, plus the authorization server's own consistency | `C`: 0 s in the reference configuration |
| Revocation propagation: form E token (F2) | A form E token stays acceptable until `exp` after the user is disabled, the consent is withdrawn, or the session is revoked, because the gateway has no status source. Microsoft describes the access token lifetime as a trade-off against "the amount of time that the client retains access after the user's account is disabled" (Microsoft: configurable token lifetimes) | At most `L`: 5400 s in the reference configuration |
| Revocation propagation: signing keys (F3) | A key that Entra ID withdraws is still accepted until the next successful refresh of the key set, and, while refreshes fail, until `T` after the last successful fetch | `K` = 3600 s; `T` = 86400 s while the key set cannot be fetched |
| Revocation propagation: form G token (F6) | A form G token stays acceptable until `exp` after the Google account is disabled, suspended or removed from the domain, or its session is revoked, because the gateway has no status source. The Workspace directory source can supply the account state, joined on `sub` ([`googledir.md`](../sources/googledir.md), GD-1, GD-7); this profile does not read it | At most `L`: 3900 s in the reference configuration |
| Revocation propagation: Google signing keys (F7) | A key that Google withdraws is still accepted until the held key set is no longer fresh under the cache headers of its response, and never longer than `T`; a key set that is no longer fresh is never used, so a source that is down defers and does not extend the window (OAUTH-43) | The freshness of the response, 20123 s in probe G2, at most `T` = 86400 s |
| Revocation propagation: enrollment (F4) and holds (F5) | Revocation, compromise mark, rotation, and holds take effect at the next request, in the consistency domain of each store (identity-mapping §7.5; draft §18) | 0 s within that domain; a replicated store declares its delay |
| Hosted domain as tenant | The tenant component of a form G principal is a domain name, the pinned `hd`, and not an immutable identifier. If the organization's domain changes, the pinned value changes and so does every identifier of the entry; an administrator re-enrolls (IM-6). The user is still named by `sub`, which Google documents as never changed | Disclosed; no bound |
| Forwarded form G token | The workload of a form G principal is the client the token was issued to, `azp` else `aud` (OAUTH-48); a gateway that receives a token forwarded by another party cannot tell the forwarder from that client | Disclosed; the holder-key proof, not the client, distinguishes the agent (draft §6.2) |
| Public clients | An allowlisted public client (`azpacr` `0`) is a registration, not an authenticated software instance; Microsoft warns that delegated tokens "can potentially be obtained by entities other than the application" (Microsoft: claims validation). The holder-key proof, not the client, distinguishes the agent (draft §6.2) | Disclosed; an entry may require `azpacr` `1` or `2` (OAUTH-30) |
| Authorization server correctness | Form I rests on the authorization server performing the checks of RFC 7662 §4 and on DR3; the adapter cannot observe them | Disclosed; DR3 |
| Sender constraints | The adapter sees the verifier's report, not the proof (OAUTH-34, DR4). Without a constraint a stolen token works as a bearer token wherever it is accepted, but cannot produce an admissible presentation, because the holder key is separate (IM-21) | Disclosed; DR4 |
| Source reference | A claim without `jti` (form I) or `uti` (form E) carries no `SourceRef`, so the monotonic guard of the freshness profile does not compare it (freshness §7) | Disclosed; no bound |
| Deployment controls | DR1 to DR7 are not observable by the adapter fixtures | Disclosed; the deployer's written statement per requirement |

## 10. Fixture index

Thirty-nine case groups cover both routes, every `closed` and `equivalently-enforced` path, the freshness rows, and the configuration-error rule of OAUTH-38; the expected results use the wording of draft §22.2 where a case applies. The groups `OAUTH-01` to `OAUTH-28` keep the numbers of the planned cases of revision `r1`, `OAUTH-29` holds the identifier cases that replace common cases, and `OAUTH-30` to `OAUTH-40` hold the cases of form G. Thirty-eight groups are adapter cases of this profile and live in `spec/v1.0/fixtures/adapters/oauth/`, each file named after its case id in lower case, such as `oauth-09.valid.json`, with the manifest id `adapters/oauth/oauth-09.valid`; `profile.json` lists the case files in `fixtures`. The [cases README](../../fixtures/adapters/oauth/README.md) defines their native state, `oauth/1`: the issuer entries and routes, the tokens, and the authorization server, discovery documents and key sets that the harness serves itself, with RSA keys it generates, so that no key is committed and no case reaches the network. It also defines the principal attributes `oauth` and `cnf`, through which `read_native_claim` and `authorize_native` receive the facts of the token authenticated for the request. A case calls one adapter function; a result that only the validator or the gateway produces (`INADMISSIBLE`, `CONTEXT_MISMATCH` from `native-principal-binding-v1`, a field rule, a receipt, a transport status) is stated with the adapter's half of it, and the rest is named in the Evidence column. A form G case gives its key set response headers (`Cache-Control`, `Age`, `Expires`, `Date`) in the member `headers` of a key set, and the harness serves them with the key set. Behaviour that needs more than one call (the introspection cache, the key-set refresh interval, a real TLS endpoint, the exact edge of a key set's freshness) is covered by Go tests of the adapter package.

## Requirement coverage

## Reference implementation (informative)

The sections above are language-neutral. The adapter of this profile is the package `go/adapters/oauth`, built with `oauth.New` from an `oauth.Config` that names the gateway's realm, the issuer entries (`oauth.Entry`), the route table with one entry and the required scope per route (`oauth.Route`), and the deployment-supplied parts. It uses the standard library only: the introspection client is `net/http`, and the RS256 verification of forms E and G is `crypto/rsa` (RSASSA-PKCS1-v1_5 with SHA-256, RFC 7518 §3.3), tested against the example of RFC 7515 Appendix A.2; `go/core/jws`, which verifies PACT artifacts, is not widened. The gateway marks requests with `oauth.Enforce` or `oauth.Mark`, a native sender-constraint verifier reports with `oauth.WithSenderProof`, and `RefreshKeys` fetches a form E or form G key set ahead. The cache headers of a form G key set are read with `net/http` header values and the rules of OAUTH-43, and tested against RFC 9111. The principal carries the attributes `oauth` (the token facts of section F) and `cnf`, which the [cases README](../../fixtures/adapters/oauth/README.md) defines. Its tests run the common cases, with the replacements of section 10, and the cases of section 10 against it, and the Go tests of the package cover `OAUTH-08`, the key-set refresh interval, a TLS endpoint, and redirects. It builds on these packages of the repository, whose names and behaviour this profile does not change.

| Package | What the adapter uses | Note |
