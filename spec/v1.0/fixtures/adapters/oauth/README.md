# OAuth adapter cases

These are the cases of the OAuth adapter of the integration profile
[`profiles/oauth`](../../../profiles/oauth/profile.md): opaque bearer tokens
validated by introspection (form I), Microsoft Entra ID v2.0 access tokens
validated locally (form E), and Google ID tokens validated locally (form G).
They run after the common cases, with the case
file format, the outcomes and the checks of [`../README.md`](../README.md).
The profile does not support clients shared by several agents, so a harness
runs the `dedicated` cases. Section 10 of the profile says which case group
each file belongs to, which behaviour is tested outside these files, and which
common cases the adapter replaces.

The cases state the adapter's configuration and every native system it talks
to in the model `oauth/1` below: the issuer entries, the authorization
server's introspection endpoint, the discovery documents and key sets of
Entra ID and Google, the tokens, and the enrollment registry. The harness serves the
endpoints itself; no case reaches the network. Keys are generated by the
harness and are never committed; no case states a signature or a key.

## Model `oauth/1`

```
{
  "model": "oauth/1",
  "gateway": {"tenant_id", "environment_id", "origin", "header_allowlist"},
  "entries": [{"id", "form", "issuer", "tenant", "audiences", "clients",
               "sender_constraint", "lifetime_seconds",
               "introspection_endpoint", "gateway_client_id",
               "gateway_client_secret", "resource_binding", "cache_seconds",
               "algorithms", "key_refresh_seconds", "key_max_age_seconds",
               "trusted_origins"}],
  "routes": [{"method", "path", "entry", "scope"}],
  "keys": [{"ref", "bits"}],
  "tokens": [{"ref", "opaque"} | {"ref", "jws": {"header", "claims", "key", "signature"}}
             | {"ref", "jwe": true}],
  "authorization": ["<field line with {token}>", ...],      // optional
  "sender_proof": {"kind"},                                   // optional
  "introspection": [{"endpoint", "token", "status", "response" | "body", "behavior"}],
  "discovery": [{"entry", "url", "status", "document"}],
  "key_sets": [{"entry", "url", "status", "headers",
                "keys": [{"key", "kid", "kty", "use", "alg", "issuer"}]}],
  "prefetch": {"entry", "at", "key_sets"},                    // optional
  "outages": ["<url>", ...],                                  // optional
  "enrollments": [...],                                       // optional
  "policy": [...],                                            // optional
  "unavailable_sources": [...]                                // optional
}
```

Times are Unix seconds.

- `gateway`: as in `common/1`. The realm of every principal is the gateway's
  realm; no token value names a realm.
- `entries`: the issuer entries of profile OAUTH-5, trusted configuration.
  `form` is `introspection` (form I), `entra-v2` (form E) or `google-id-token`
  (form G). `issuer` is the issuer identifier and `tenant` the tenant
  component of OAUTH-37: for form E the tenant ID, for form G the pinned
  hosted domain (`hd`), for form I the configured tenant or `none`. `audiences` are
  the accepted audience values, `clients` the client allowlist, and
  `sender_constraint` is `none`, `dpop` or `mtls` (OAUTH-34).
  `lifetime_seconds` is the lifetime bound `L`. Form I entries also carry the
  introspection endpoint, the gateway's own client credentials for it,
  `resource_binding` (`aud` or `introspection-scoped`, OAUTH-13) and the
  cache bound `C` as `cache_seconds`. Form E and form G entries carry the
  algorithm allowlist, the key-set bounds `K` and `T` (OAUTH-24, OAUTH-43)
  and the trusted origins of the key set. A form G entry's `audiences` are
  the application's OAuth client IDs and its `clients` the client allowlist
  of OAUTH-48.
- `routes`: the route table of OAUTH-6. A route matches a method and a path
  template in which `{name}` stands for one path segment, names the one entry
  that authenticates it, and gives the required delegated scope of OAUTH-31;
  an empty `scope` requires none.
- `keys`: the RSA keys of the case, each of `bits` bits, generated by the
  harness on first use. A case never states a key's value.
- `tokens`: what clients hold. `opaque` is the token text of form I. `jws` is
  a token the harness mints in compact serialization: the JSON `header` and
  `claims`, signed with the key `key`. A header member whose value is
  `@public:<ref>` is replaced by the RSA public JWK of that key (`kty`, `n`,
  `e`). `signature` is `valid` (the default: RSASSA-PKCS1-v1_5 with SHA-256
  for `alg` `RS256`, RSASSA-PSS with SHA-256 and a salt of 32 octets for
  `PS256`, RFC 7518 sections 3.3 and 3.5), `altered` (a valid signature with
  one bit flipped), `empty` (an empty signature segment), or
  `hs256-public-key` (HMAC-SHA-256 keyed with the DER SubjectPublicKeyInfo of
  the key's public part, the algorithm-confusion attack of RFC 8725
  section 2.1). `jwe` is a token of five base64url segments.
- `authorization`: the `Authorization` field lines the credential hook adds,
  in order, with `{token}` replaced by the text of the presented token.
  Absent, it is the one line `Bearer {token}`.
- `sender_proof`: the report of the deployment's native sender-constraint
  verifier (profile DR4) that this request's proof was verified, `kind`
  `dpop` or `mtls`. The harness attaches it through the adapter's
  authenticated request context, never as a header. Absent, no verifier
  reported.
- `introspection`: the authorization server's answers, by endpoint and token
  text. The harness's endpoint requires what RFC 7662 section 2.1 and
  profile OAUTH-7 and OAUTH-8 ask of the gateway: `POST`,
  `application/x-www-form-urlencoded` with `token` and
  `token_type_hint=access_token`, and the gateway's client credentials in
  HTTP Basic, each form-urlencoded (RFC 6749 section 2.3.1); otherwise it
  answers 400 or 401. It answers a record with `status` and either
  `response`, a JSON object, or `body`, the exact octets as a string, which
  can hold a duplicate member or text that is not JSON. `behavior` `timeout`
  never answers. A token without a record is `{"active": false}`.
- `discovery`: the OpenID Connect discovery document served at `url` for the
  entry `entry`, with its HTTP status.
- `key_sets`: the JWK Set served at `url`: one member per entry of `keys`,
  the RSA public key of `key` with the members `kty`, `kid`, `use`, `alg` and
  `issuer` as given (`use`, `alg` and `issuer` only when given). `headers`,
  when present, are HTTP response header fields of the answer, name to value,
  such as `Cache-Control` and `Age`, which form G reads (OAUTH-43).
- `prefetch`: before the case's call the harness lets the adapter fetch the
  key set of `entry` at the instant `at`, from `key_sets` when the prefetch
  gives them and from the state's otherwise, with no outage. The adapter then
  holds a key set fetched at `at`.
- `outages`: URLs whose connection fails during the case's call.
- `enrollments`, `policy`, `unavailable_sources`: as in `common/1`.

### Hooks

The harness's transport fires a hook for every request the adapter sends,
except during a prefetch: `introspect:<entry>` for the introspection
endpoint of an entry, `discover:<entry>` and `fetch-keys:<entry>` for the
discovery document and the key set of an entry, and `fetch-untrusted` for
any other URL, which it answers with 404. A case lists in
`expect.must_not_call` the requests the adapter must not make, such as the
introspection of a token on a form E route, or a fetch of a `jku` URL.

### Credentials

`request.native_state_ref` names a token. The harness's credential hook adds
the `Authorization` field lines of `authorization` with that token, and
attaches `sender_proof` when the state has one. A request without
`native_state_ref` carries only the headers the case gives.

### Principal attributes

An authenticated principal of this adapter has the mechanism `oauth` and
reports the facts of its token in the attribute `oauth`, which
`read_native_claim` and `authorize_native` read when they are given the
principal (profile section F and OAUTH-31):

```
"oauth": {"entry", "form", "tenant", "scopes", "issued_at",
          "status_checked_at", "token_id"}
```

`entry` is the issuer entry and the source of every claim; `form` is
`introspection`, `entra-v2` or `google-id-token`; `tenant` the tenant
component of the principal; `scopes` the scope list of OAUTH-14 or OAUTH-31 in
the order issued; `issued_at` the token's `iat`; `status_checked_at`, in form I
only, the instant the introspection request was sent; `token_id` the `jti`
(form I) or `uti` (form E). A form G token gives no `token_id`, and its `scopes`
is empty. A member the token does not give is absent. A token bound
by `cnf` (OAUTH-34) is reported in the attribute `cnf`, as `{"jkt": ...}` or
`{"x5t#S256": ...}`, which never enrolls the key (IM-21).

## Common cases

The common cases state their native state in `common/1`. An OAuth harness
realizes it with one form I issuer entry that serves every route. When every
identity of the state has an `oauth:` identifier of one issuer and one tenant,
the entry has that issuer and tenant, and each identity's `secret` is an
opaque token that introspects to the identity's subject and the client of its
workload; otherwise the entry has the issuer `https://as.common.example` and
the tenant `none`, and an identity introspects to the subject and client
named by its `ref`. The other functions use the deployment-supplied sources
that `common/1` describes. Six common `authenticate_native` cases expect a
principal that a token of this profile cannot yield and are replaced
(profile section 10; adapters README, "Replaced common cases").
