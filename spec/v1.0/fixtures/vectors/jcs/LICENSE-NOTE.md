| Path | Relation to upstream |
|------|----------------------|

| `numbers.json` | Modified. See below. |

| `LICENSE-2.0.md`, `LICENSE-NOTE.md` | Not upstream files. |

JSON has no comments, so this file is the notice of the changes that section
4(b) of the license asks for; no data file carries one itself.

The upstream `outhex/` files (the same outputs in hexadecimal notation) are
not copied; they carry no information beyond `output/`.

`numbers.json` is a changed form of the first 10000 lines of the upstream
number file `es6testfile100m.txt`. Upstream publishes that file as lines of
`hex-ieee,expected`, with the hex part of 1 to 16 digits. Changes made here:

- The lines are a JSON array of `{"ieee754_hex", "expected"}` objects, one per
  line, in upstream order.
- `ieee754_hex` is the upstream hex part, left-padded with zeros to 16 digits,
  lowercase.
- `expected` is the upstream text, unchanged.
- Lines beyond the first 10000 are omitted.

The first 10000 lines were regenerated with upstream `numgen.go` (only the
line count changed) rather than cut from the 100-million-line download. The
SHA-256 of the regenerated text matches the checksum table in upstream
`testdata/README.md`: `be18b62b6f69cdab33a7e0dae0d9cfa869fda80ddc712221570f9f40a5878687`
for the first 1000 lines and
`b9f7a8e75ef22a835685a52ccba7f7d6bdc99e34b010992cbc5864cd12be6892` for the
first 10000. Undoing the changes above (hex without leading zeros, one
`hex,expected` line each) gives text with those same checksums. The sample
contains every RFC 8785 Appendix B value except NaN and Infinity, which JSON
cannot carry.

## Use

Each file is registered in `../../manifest.json` under an id that starts with
`vectors/jcs/`. Every consumer applies the same two rules:

- An entry whose `path` and `expected` differ is an input and output pair.
  Canonicalize the exact bytes of `path`. The result must equal the exact bytes
  of `expected`. The output files have no trailing newline.
- The entry `vectors/jcs/numbers` has the same file in `path` and `expected`.
  For each element, read `ieee754_hex` as the big-endian bit pattern of an
  IEEE 754 binary64 value and serialize that value as an RFC 8785 number. The
  result must equal `expected`.
