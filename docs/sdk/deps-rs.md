# Rust dependencies

This file registers third-party Rust crates for the PACT protocol's Rust SDK (the `rs/` crate, `hop-top-pact`). The candidates and their feature sets come from the probe record [`probes/rs.md`](probes/rs.md). A crate reaches `Cargo.toml` only after a vet with `rsx` in deep mode (`rsx analyze <owner/repo> --mode deep`) passes the balanced policy check (`rsx policy test <owner/repo> --policy-profile balanced --mode deep`). A failure is recorded here instead of a pin. Each row captures what `rsx` reported plus separately verified facts – anything not verified is marked "to verify". The dependency line itself is added in the scaffold work, not here. Rows are appended as crates are vetted; existing rows are only edited to correct them or record a re-vet.

The first vets ran on 2026-10-16; the `regex` and `getrandom` rows and the scaffold results below are from 2026-10-20. `rsx` scores a GitHub repository, not a crate: the RustCrypto crates live in monorepos, so `p256` and `sha2` carry the score of `RustCrypto/elliptic-curves` and `RustCrypto/hashes`.

- **Crate** – the crates.io name and the GitHub repository slug that crates.io lists for it (`repository` field of the crate metadata, matching the `Cargo.toml` inside the published `.crate`)
- **Used by** – the SDK function that needs it
- **Version to pin** – the exact version (`=x.y.z` in `Cargo.toml`), the feature set to enable, and the declared minimum Rust version (the repository's toolchain pin is 1.99.1)
- **License** – the SPDX expression from crates.io, checked against the license files inside the published `.crate`
- **Maintenance** – `rsx` maintenance signals and separately verified facts, including the publication date of the pinned version (crates.io, UTC)
- **rsx verdict** – the `rsx` result under the balanced policy, with the date of the vet
- **Constraint** – where the crate may or may not be used, which features must stay off; `none` when there is no constraint

## Scaffold results

Recorded 2026-10-20, when the scaffold pinned the rows above in `rs/Cargo.toml` with exact (`=`) versions and `rs/Cargo.lock` was committed.

- Resolution: `cargo tree -e normal,build` resolves 96 crates, the SDK and the 95 of the probe's `sdk-set-jsonschema` line, at the probe's versions, and 97 with `getrandom`; every directly named crate is at the version of its row. The dev-dependency `serde_json_canonicalizer` adds `ryu-js` 1.0.3.
- `rsx audit rs/` read the normal dependencies of `rs/Cargo.toml` and resolved none of them to a repository (`unresolved 6`, no analyses): it has no crates.io resolver for this manifest. The per-crate vets above stand in for it.
- OSV, queried by name and version for the 111 crate versions of `rs/Cargo.lock` (normal, build and dev): 0 findings.
- `base64`: pinned with `default-features = false, features = ["std"]`, so `simd-unsafe` is off and the crate is `#![forbid(unsafe_code)]`. The unit test of `rs/src/core/jws/base64url.rs` checks, with that feature set, that `URL_SAFE_NO_PAD` rejects padding, the standard alphabet, a line feed, a space, non-canonical trailing bits, a length of 1 mod 4 and non-ASCII input, and decodes the empty string; the shared JWS vectors `es256-signature-padded`, `es256-signature-std-alphabet`, `es256-signature-noncanonical` and `compact-payload-line-break` pass through it.
- Freshness: the vetted versions are pinned, not newer ones. On 2026-10-20 they are the latest stable releases; `jsonschema` `0.59.0` replaced `0.58.6` that day (see "Update check").
- `serde_jcs` is not taken: `serde_json_canonicalizer` is the one test oracle of the in-house canonicalizer (the 10000-row and pair vectors run in the SDK's own tests).
- `ring` and `boon` stay unselected; `p256` 0.14.0 with a hand-built JWK, as the probe decided.
- `format: uri`: with format assertion on and no checker registered, `jsonschema` 0.58.6 gives the verdict of the shared expression on every row of `uri-format.json`, on 26 hand-picked strings (IPv6 zone identifiers, IPvFuture, bad percent escapes, repeated `@`, an empty or unclosed IP literal) and on 200000 pseudo-random strings over the URI delimiters, `\`, a space, `é`, U+212A and a line feed: 0 differences (probe run as a scratch test, 2026-10-20). The schema module registers the shared expression all the same, so the verdict does not depend on the library's checker; a mutation that drops the registration is therefore not detectable by any vector and has no patch.
- Ed25519: no crate is vetted, so the SDK implements ES256 alone and declares no `jws-ed25519` capability.

## Dependency guard

`rs/tests/depcheck.rs` runs with `cargo test` (`make rs-test`) and checks:

- `[dependencies]`, `[dev-dependencies]` and `[build-dependencies]` of `rs/Cargo.toml` hold exactly the entries of `rs/tests/support/deps.toml`: the same crates, each an exact `=x.y.z` pin, the same `default-features` and the same features. An entry may carry only `version`, `default-features` and `features`, so a `git`, `path`, `registry`, renamed or optional dependency is rejected. No other dependency table (`[target.*.dependencies]`, `[dependencies.<name>]`), `[patch]`, `[replace]` or `[workspace]` is allowed.
- `rs/Cargo.lock` holds exactly the `[lock]` entries of that file (name, version and checksum), all from crates.io, plus the crate itself, and each pinned crate at its pinned version.
- `src/` and `examples/` name no dev-only crate, and no file under `src/`, `tests/` or `examples/` uses a private path (a segment starting with `__`, such as `serde::__private`) of a dependency.
- In the source repository (`PACT_REQUIRE_VECTORS=1`), this file agrees with `deps.toml`: every runtime crate has a row in "Vetted dependencies" and every row there is a runtime crate; every dev or build crate has a row in "Vetted dev-only dependencies"; each row's version is the pin, its version cell says `default-features = false` exactly when the pin turns the defaults off, and it names each enabled feature; and the list under "Locked crate versions" is the `[lock]` set.

A negative control in the same test feeds the checks a manifest, a lock, sources and a copy of this file with unvetted or altered entries and requires each to be reported.

## Method and caveats

- Slugs: taken from the `repository` field of the crates.io metadata (`https://crates.io/api/v1/crates/<name>`), which matches the `Cargo.toml` inside each downloaded `.crate`. Each `.crate` was checked against the crates.io SHA-256 checksum before its license files were read.
- Dates, versions, MSRV, license and feature tables: crates.io metadata for the pinned version. Tag dates: GitHub tags of each repository (`ring` has none).
- `rsx` runs: `rsx analyze <owner/repo> --mode deep` and `rsx policy test <owner/repo> --policy-profile balanced --mode deep` for every slug (identical scores and verdict in both), and `rsx compare` for the schema validators, the ES256 candidates and the two JCS oracles. Every policy test exited 0.
- What `rsx` does not measure: its adoption score derives dependents from stars (`rsx` evidence key `dependents_count`, "stars/20 estimate; dependents not sampled"), so adoption is not a real usage signal; its commit cadence and "last maintainer activity" are merged-PR stand-ins; its release hygiene is low for repositories that tag but publish no GitHub releases (RustCrypto, `serde`, `ring`); its license score is 3.0/10 where a monorepo has no root license file; its Scorecard "Vulnerabilities" check scans the repository's own lock files, not the dependency resolution of a published crate.
- Advisory sources: the RustSec advisory database (`rustsec/advisory-db`, commit `479c888ce4`, 2026-10-16) per crate name, the repository advisory lists on GitHub where `rsx` counted any, and OSV queried by crate and version.
